# Internationalization (i18n) Guidelines

> **Library:** `next-intl`  
> **Dictionaries:** `dictionaries/*.json` (default: `dictionaries/en.json`)  
> **Type Safety:** `global.d.ts` via `AppConfig` module augmentation

---

## Core Rule: Always Use Translations

**Never hardcode user-facing copy in pages, components, forms, or error messages.**

Every user-facing string—including titles, descriptions, placeholders, button labels, and error messages—must be defined in the dictionary files and referenced via `next-intl`.

---

## Dictionary Structure

- Store dictionary files in `dictionaries/{locale}.json` (e.g. `dictionaries/en.json`).
- Structure keys hierarchically by page or feature namespace:

```json
{
  "HomePage": {
    "title": "Buttler"
  },
  "LoginPage": {
    "title": "Sign in to Buttler",
    "description": "Authenticate with your GitHub account to continue.",
    "continueWithGitHub": "Continue with GitHub",
    "errors": {
      "github": "GitHub authentication failed. Please try again."
    }
  }
}
```

---

## Usage in Server Components

In Server Components (layouts, pages), always use `getTranslations` from `next-intl/server`:

```tsx
import { getTranslations } from "next-intl/server";

const Page = async () => {
  const t = await getTranslations("HomePage");

  return <h1>{t("title")}</h1>;
};
```

---

## Usage in Client Components

For Client Components (`"use client"`), pass translated strings as props from the parent Server Component:

```tsx
// Server Component (e.g. page.tsx)
<ManifestForm
  labels={{
    appNameLabel: t("manifest.appNameLabel"),
    submit: t("manifest.submit"),
  }}
/>
```

This keeps Client Components pure, avoids unnecessary client message bundle overhead, and maintains compatibility with static shells and instant navigation.

---

## Type Safety

The project uses `global.d.ts` to augment `next-intl`'s `AppConfig.Messages` with the schema of `dictionaries/en.json`. All `t(...)` keys are strictly type-checked at compile time:

```bash
npx tsc --noEmit
```
